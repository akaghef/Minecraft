# 既存計算機の起動・観測・照合

2026-11-23に、コピーしたCalculator_Developの保存済みチャンク全体を読み取った。27個のregion/entitiesファイル、8,008チャンクにコマンドブロック21個、データパック関数19本があった。チャンク読取エラーはなかった。原本ワールドは起動・編集対象にしない。

## 操作の入口

既存の`config/cmdkeybindconfig.json5`に残っている割当。コマンドの呼出しは実行確認済みだが、キーボード操作そのものの再試験とは区別する。

| キー | コマンド | 設定上の動作 |
|---|---|---|
| `.` | `/function c:pulse1` | Repeating、3,000 ms間隔 |
| `,` | `/function c:pulse2` | SingleUse |
| 左Command＋`F` | `/tick freeze` | 停止・再開 |
| `J` / 左Command＋`J` | `/tick step 2` / `4` | Repeating、200 ms間隔 |
| `K` / 左Command＋`K` | `/tick step 12` / `120` | Repeating |
| `'` | `/tick step 8` | SingleUse |

`pulse1`は`(92,-49,76)`、`pulse2`は`(92,-49,64)`へ赤石ブロックを置き、4ゲームティック後に撤去する。既存MATLABの`Debug/pulse.m`では1がset、2がresetと記載されている。今回の回路試験はこの関数を使った。`/tick rate 50`もDisplayOnly設定として残っているが、今回の試験では実行していない。

## 観測の流れ

繰り返しコマンドブロック`(76,-60,63)`が`c:loop_val`を呼び、比較器の`OutputSignal`をスコアボード`Val`へ保存する。`c:tell_val`を呼ぶブロックは`(107,-52,78)`にある。

| チャットの系列 | 観測内容 |
|---|---|
| `val:1` | A、13桁、上位桁から出力し末尾に時刻 |
| `val:2` | M1、同上 |
| `val:3` | M2、同上 |
| `val:4` | M4、同上 |
| `val:5` | 符号観測点`(106,-30,71)` |
| `time:0 0` | ログ区間の開始マーカー |
| `time:1`～`time:8` | `getLog.m`でI12、O12、S12s、S12e、O3、U1、U2、O4へ対応付け |

`getVal2.m`/`kensyou.m`はAの各桁から1、M4の各桁から2を引き、負になった桁を0へ丸めて数値を復元する。その後、3相の観測値を並べ直し、`cordic_latest.m`の角度残差・正弦・余弦・補助値・時刻と照合する。生の信号強度は復元値と併記して保持する。

## アカウント変更への修正

従来は毎ティック`@a time`へ5加算しながら、ログ出力と時刻リセットは旧プレイヤー名の`time`を参照していた。保存データでも旧名の時刻が30、現在のプレイヤー側が1,011,070となっており、観測時刻が追従していなかった。

コピー側のコマンドブロック10個と関数3本を、プレイヤー名を使わない`#clock time`へ統一した。加算は1ゲームティック当たり5。`val:`/`time:`の形式は維持した。MATLABのコマンド生成箇所も同じ参照へ変更した。

実クライアントで`c:tell_val`を実行し、チャットログの4系列×13桁が、同時点の比較器の直接読取と一致した。専用サーバー側ではカウンターの増分も確認した。これらは観測経路の確認であり、演算の合格とは扱わない。

修正後のコマンドブロックは保存済みregionファイルを再読込して確認した。統合サーバーの保存には、[1.20.1のsaveAll API](https://maven.fabricmc.net/docs/yarn-1.20.1%2Bbuild.10/net/minecraft/server/MinecraftServer.html#saveAll(boolean,boolean,boolean))を使用する。旧試験用`c:test`には先頭スラッシュによる読込エラーがあり、`c:setpulse`と`test:setpulse2`にも未定義関数への参照が残る。今回確認した起動経路は`c:pulse1`/`c:pulse2`である。

## 完了を確認したリセットと起動

リセット関数を呼んだことと、内部の初期化完了は区別する。検証用コピーをCarpetで停止した状態から、次の順に操作した。

1. `/function c:pulse2`を1回実行する。
2. `/tick freeze`で進行を再開する。停止したまま実時間を待ってもリセットは進まない。
3. 開始から最低100ゲームティック待つ。さらに、13桁すべてでAの生信号強度が1以下、M1・M2・Iが0の状態が24ゲームティック以上連続することを観測する。
4. 両条件を満たしてから`/function c:pulse1`を1回実行する。手動の`.`はRepeating設定なので連続起動に注意する。
5. 回路自身の停止まで全ティックを収録し、最後の完全な3相から正弦・余弦を復元する。

100ゲームティックは通常速度で5秒、24ゲームティックはパイプライン2周分。最初の2回の成功実行では、起動時点でクリア状態が62ゲームティック連続していた。この条件はデータ経路のクリアを確認するもので、全制御状態に対する専用のreset完了信号を同定したという意味ではない。

## 完全ログからの正弦・余弦の復元

元の`getLog.m`は時計を10で割ってレッドストーンティックへ変換する。`getVal2.m`の位相式は`floor(mod(T_rst+4,6)/2)`。1ゲームティック当たり時計が5増えるので、位相は`floor(((clock+40) mod 60)/20)`となり、0が角度残差、1が正弦、2が余弦。値がモデルに近くなるように位相を選んだものではない。

各相の末尾に当たる`clock mod 20 = 0`で読む。スコアボード上のAは、`(Au−1800000000)×10^7 + (Al−1700000000)`で復元する。比較器の直接読取による桁オフセット除去、および既存チャット処理の負桁を0へ丸める方法と、終点の3相が一致することも検査する。

時計は起動時に0へ戻るため、リセット前後を別区間として扱う。最終周期は時計の大小でなく観測順から選ぶ。最後の不完全周期に正弦または余弦が残っていれば、それが直前の完全周期と同値であることも確認する。

## 現在の実回路の照合結果

初期化完了を待つ手順で、同じ回路を2回動かし、どちらも回路自身の停止まで収録した。角度の読込段で`1230000000000`、すなわち12.3度相当を実測した。入力値を外から新たに設定した実験ではなく、外部の入力設定場所はまだ同定していない。

| 最終値 | 実回路・1回目 | 実回路・2回目 | 既存モデル |
|---|---:|---:|---:|
| 正弦 | 0.213030386282 | 0.213030386282 | 0.213030386282 |
| 余弦 | 0.977045574430 | 0.977045574430 | 0.977045574430 |

両実行とも固定小数点の整数値まで一致した（倍率10^12、差0）。各実行の終点では完全な4周期が同じ正弦・余弦を保持し、後続の不完全周期も同値だった。最終完全周期の正弦は時計15640、余弦は15660で、角度残差は13桁表現で9999999999971だった。[1回目の観測値](../verification/calculator-reset-confirmed-output.json)、[2回目の観測値](../verification/calculator-reset-repeat-output.json)、[モデルとの比較](../verification/calculator-model-paired-output.json)を保存する。

モデルは既存の`calculator/audit/crosscheck.py`を使用し、保存済みMATLAB結果5例とも照合している。追加のMathWorksサインインやMATLABの新規起動は行わない。演算本体、定数表、信号強度の規則、ティック速度、モデルの演算、合格条件は今回の成功のために変更していない。

## 初期の不一致と過去ログ

最初の起動では、進行中にリセットを発行してから約95ゲームティック後に起動し、初期化完了を確認しなかった。最初の粗回転でM1・M2のシフト量が10倍異なり、最後は正弦0.590030184104、余弦0.664081472235だった。この[失敗ログの最終値](../verification/calculator-physical-final-output.json)と[途中の比較](../verification/calculator-core-first-step.json)は保持する。

その後、停止中にリセットを準備して再開し、上記の待機・クリア状態確認を行うと不一致は解消した。リセット発行時の停止状態と待機条件を同時に変えているため、95と100ゲームティックの差だけが原因だったとは断定しない。起動前の初期化条件に依存する再現結果であり、回路自体の不良とは扱わない。

初期診断で`R0input / adjust shift num`付近の定数を2から1へ変えると初期ゲイン自体が10分の1になったが、この試験は合格の証拠に使わず、定数を2へ戻した。成功した実行では元の定数を使用している。保存済みcalc240531との比較でも、コアのブロック配置・静的状態・樽の内容は一致した。

元の圧縮ゲームログも調べた。`2024-05-31-1.log.gz`の開始マーカー後の第6区間には、時刻20刻みで752組の完全な観測がある。12.3度相当の角度から、最後の完全周期の正弦0.213030386686、余弦0.977045574748を復元した。[過去ログの復元結果](../verification/calculator-historical-readout.json)を現行実行と分けて保存する。このログは同日のcalc240531保存時刻より前であり、現在と同じ回路版とは断定しない。

## 再実行の入口と確認範囲

`scripts/record_core_readout.js`は、専用の複製インスタンスを停止した状態で使用する。期待出力を回路へ与えず、初期化の観測・起動・65個の生信号強度と時計の全ティック収録を行う。回路自身の停止で記録を終え、7,000ティックで停止しなければ上限到達として記録する。既存ログは上書きしない。

`scripts/decode_core_readout.py`は完全ログから両出力を復元する。途中終了、観測エラー、復元方式の不一致、後続相での値の変化はエラーにする。使用方法は[ローカルでの入口](setup.md)を参照する。

今回確認したのは、このコピーが読み込んだ12.3度相当のケースでの合致。モデルの全入力に対する誤差上界を、そのまま実機の精度保証にはしない。次の拡張は、外部入力設定場所を同定し、別の角度でも同じリセット・読込・照合を行うこと。

全コマンド、変更前後、チャット、生のティック観測、ワールドの退避コピーは非公開の`.local/verification/calculator-develop-debugger/`へ保存する。`scripts/extract_world_debugger.py`は既存NBTライブラリで保存データを読み取る。
